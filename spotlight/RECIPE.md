# Spotlight for Herdr

Orca Pro Max's Spotlight and test queue as a Herdr plugin. One dev server per repo runs at the repo ROOT, with the code of the workspace that holds the Spotlight projected there. Agents read its logs and restart it with the CLI, and take test turns through a queue: one per space, a global cap, and a pause when the account hits its usage limit.

- The mod is in `mods/spotlight/`. It shows the footer flask, the queue board, settings, the server popup, and the badges on projects-sidebar rows.
- The engine is the `spotlight` CLI, in `mods/spotlight/cli.mjs` and `bin/spotlight`.
- State lives in `~/.config/herdr-app/spotlight/`; logs in `~/.local/state/herdr-spotlight/logs/`.

Being built (ODD plan `odd/tasks/spotlight.md`, kept out of git). Verbs and probes get documented here as each task lands.

## Install

From the repo root:

```sh
scripts/install.sh            # projects-sidebar, which requires spotlight: both land, spotlight first
scripts/install.sh spotlight  # spotlight alone
scripts/install.sh --uninstall spotlight
```

- The installer copies `mods/spotlight/` into `~/.config/herdr-app/mods/`, with the CLI inside it, since Herdr doesn't load a symlinked mod. After an edit, run it again and Herdr hot-reloads the copy.
- It links `~/.local/bin/spotlight` to the installed `mods/spotlight/bin/spotlight`, as the plugin's `bin` file asks, so agents, the harness hook and badge clicks run `spotlight` by name. Herdr's exec PATH starts with `~/.local/bin`.
- The mod and the link are both listed in `~/.config/herdr-app/.herdr-plugins/spotlight.txt`. A `~/.local/bin/spotlight` that isn't that link stops the install before anything changes. `--uninstall` removes the mod and the link.
- `bin/spotlight` follows its own links to the mod folder. It runs `cli.mjs` on the `node` found on PATH, else `/opt/homebrew/bin/node`, else `/usr/local/bin/node`.
- The footer is a block in projects-sidebar's layout (D20, the way claude-accounts got its usage block). It shows the flask and is the copy that runs the reaper, badges and auto-sync.
  - The block: `layouts/projects.json` has `status-spotlight` (px 40, `{"mod": "spotlight", "props": {"view": "footer"}}`) in the status row, between `workspace-status` and claude-accounts' usage.
  - `projects-sidebar/requires` lists `spotlight`, so installing projects-sidebar installs this plugin first. Without it, the block shows "spotlight did not load".
  - With another layout shown, no footer copy runs. Its `close` clears `badges.spotlight`, so no stale badge stays, and `spotlight on` still syncs and reaps for agents.

## Server terminal probe

Probed 2026-11-06 against Herdr's hc, on a throwaway terminal `sl-probe` (created and removed each time). `mods/spotlight/server.js` relies on what it showed.

- The server line runs on the shell's Node. Typed into a `zsh -l` terminal, `script -F -q -a <log> /bin/zsh -c '…'` resolved `node` to the same nvm Node as `command -v node` outside it (v24.14.0), not Homebrew's.
- The log file keeps everything. After `seq 1 500` it held all 500 lines. After `seq 1 50000` it held all 50,000, written as they were printed. Lines end in CRLF, so strip `\r` before counting with `grep -x`: BSD grep miscounted one line.
- `hc read` is only a fallback. `hc read <t> --lines 600` returned all 500 lines. With 50,000 lines printed, `--lines 100000` returned only the last ~2,640, with `complete: false`. So `spotlight logs` reads the file, and uses `hc read` only when the file is missing.
- Ownership. While the server runs, `hc get --json` shows `foreground.argv = ["script","-F","-q","-a","<log>","/bin/zsh","-c","<line>"]`, with `name: "script"` and its own pid. With the prompt free, `foreground.pid` equals the terminal's `pid` (the `zsh -l`).
- Ports. The process tree is zsh -l → script → the server: zsh's `-c` execs the last command. `pgrep -P` walks it from the terminal's `pid`, and `lsof -F pcn` lists the listening socket under the server's pid.
- Interrupt. `hc interrupt` sent ctrl+c and answered `"outcome": "stopped"`, but `script` was still the foreground on the next `hc get`; the prompt came back a moment later. Restart and stop therefore poll for the prompt before typing again. The server log shows `^C`.
- hc's answers:
  - `hc get` of a missing terminal exits 3 with `{"error":{"kind":"not_found"}}`.
  - Running a second live terminal under a taken name exits 1 with `name_taken`.
  - `hc send` to a finished terminal exits 11 with `finished`.
  - After `hc kill`, the terminal reads `state: "finished"`, `reason: "killed"`, with no `foreground`. `hc get <name>` still finds it until `hc rm`, so `server.js` removes a finished server terminal before creating a new one.
  - `hc run --json` prints the new terminal's `address`.
- The probe's terminal was hidden. Since T29 the server terminal also carries `--label herdr.space=<id>` whenever Herdr says where the root is, and shows as the root's "Spotlight" tab; the rest of its argv, the typed line and the log are the ones above. See "Where the server shows".

## Where the server shows

The server runs in the root's main terminal, as in Orca (D38): a tab named "Spotlight" in the root's space. Orca types the server line into that terminal after a Ctrl-C; here Spotlight's own terminal takes its place, so the agents' log keeps its `script -F` mirror from the terminal's first line.

- The root's space is the first space of this machine in `herdr-app ls` whose place is the root: its first terminal's live folder (the `cwd` of `hc ls --json`), else the folder it was made in, projects-sidebar's rule. With none, Spotlight uses a fresh id (`sp` + 32 hex characters) and Herdr makes a space named after the root's folder.
- Which terminal, in Orca's order:
  1. Spotlight's own (labelled `spotlight.repo=<root>`: the recorded address, else `sl-<slug>`), when live, is reused as it is. One Herdr shows nowhere (no `herdr.space`: lit before T29, or made while Herdr couldn't say) is shown first: `hc label <t> herdr.space=<id>`, then its tab is renamed "Spotlight". No restart, no other terminal touched. The reap does this for a lit repo's running server, and every start or restart does it for the terminal it uses.
  2. Otherwise, in the root's space, the active tab's first plain terminal, else the first plain one in tab order. Plain means `app: null` in `herdr-app ls`: a shell, whatever runs in it. Never an agent's terminal (`app` set, or not given), never any repo's Spotlight terminal (its `spotlight.repo` label, read with `hc get`), never one hc doesn't read as live.
  3. Otherwise (no plain terminal, or no space yet), a new tab.
- Replacing a terminal, in this order: Spotlight's terminal is made as always plus `--label herdr.space=<id>`; its tab is renamed "Spotlight" (`tab.rename`) and moved to the replaced terminal's tab's place (`tab.move`); then the replaced terminal is killed (`hc kill`), whatever ran in it, and Spotlight waits up to 5 s for hc to read it finished. Being made before the kill, the new tab keeps the space from emptying (an emptied space closes). Only that terminal goes: another pane of its tab stays, in its tab. Its scrollback goes with it, a difference from Orca.
- A new tab is named "Spotlight" and left where Herdr puts it, at the end.
- Nothing asks for the focus while lighting: no `space.select`, `tab.select` or `pane.focus`.
- The kill comes before the port check (D24). A server started by hand in the replaced terminal dies with it, and the check asks again for up to 3 s while it lets go of its port. A listener anywhere else is still `port-busy`, with nothing typed; the record keeps the new terminal.
- When `herdr-app ls` fails or lists no spaces, Herdr can't say where the root is: the terminal is made hidden, as before T29, and the next reap shows it. When Herdr doesn't show a new terminal in a tab within 3 s, it isn't renamed or moved and nothing is killed.
- "Ver server" (the popup, `spotlight peek`) selects the server's space, then its tab (`space.select`, `tab.select`, by id), instead of opening the peek. A server terminal in no tab still gets Herdr's peek over the tab.
- Closing the tab, or its space, ends the server terminal. The reap reads it `gone` and toasts once (see "A server that ends by hand"), and Reiniciar makes the tab again by the same rule.
- The turn-off, the log mirror and `spotlight logs` are unchanged (see "Turning the server off"): the terminal and its tab stay, at a free prompt, for the next start.
- Herdr commands go as `herdr-app do <command> '<args as JSON>'`, since `tab.move`'s index (1 = first) is a number.
- Probed live on 2026-11-08 (D38):
  - `herdr-app ls` lists spaces → tabs → terminals; each terminal is `{terminal, pane, name, status, app, sub_agents}`, with `app` null for a plain shell.
  - `hc run --bg --keep --no-parent … --label herdr.space=<id>` puts the terminal in a new tab of that space and leaves the focused space alone. An id Herdr doesn't know makes a space named after the cwd's folder, also without focus.
  - `hc label <t> herdr.space=<id>` on a running hidden terminal shows it as a tab at once. `herdr-app do tab.rename {id, name}` names it.
  - Killing a terminal removes its tab, and a space left with no tab closes.
  - Not probed: whether `tab.move` counts settled tabs. Spotlight counts every tab `herdr-app ls` lists.
- The pieces are `server.js` (`findRootSpace`, `ensureServerTerminal`, `serverTerminalHidden`, `showServerTerminal`, `showServer`), `cli-work.mjs` (`ensureServer`, which ensures the terminal before the port check, and the reap's `showHiddenServer`) and `cli.mjs` (`peek`).

## Badge command probe

Probed 2026-11-06 in Herdr 0.1.13, with a throwaway mod (`zz-sl-cmd-probe`, `{"place":"none"}`, shown as a `kind: "window"` overlay through `mod.open`, then closed and its folder removed). `badges.js` relies on what it showed.

- Dynamic command names reach `nextCommand()`. `herdr-app do zz-sl-cmd-probe.server.0a1b2c3d4e5f` from a shell, and `run("zz-sl-cmd-probe.server.fedcba987654")` from inside a mod (what projects-sidebar's badge click does), both arrived. `nextCommand()` yielded `server.0a1b2c3d4e5f` and `server.fedcba987654`: the name without the mod's prefix, dots kept. So the server badge uses `{ "command": "spotlight.server.<id>" }`, and D17's exec fallback (`ui.request` in state.json) isn't needed.
- With no shown copy, Herdr refuses the command (`unknown command "…": a mod's are <mod>.<command> and need the mod loaded`) and doesn't queue it: a copy opened afterwards got nothing. So the server badge and the error toasts open the popup only while the footer copy is in the layout (D20).
- What remains: Herdr's `seen.json` keeps the probe's name, as it keeps every mod folder it has seen.

## Badges, auto-sync and the server popup

- `badges.js` (footer copy only) publishes `badges.spotlight` per projects-sidebar's contract: a flashlight (amber on the holder's and the root's rows, dim on the other worktrees of an enabled repo, red on an error), the server (`:3000`, `:3000+1`, `…`, red when stopped or gone) and the queue state (flask, clock + `#N`, pause), at most three per row, written only when the value changes. The model is `badges-model.js`.
- The server badge's id is the first 12 hex chars of sha1(workspace path), the same id the CLI puts in its error toasts' action (`cli-work.mjs` serverId). `badges-model.js` computes SHA-1 itself, so the id doesn't depend on the runtime's crypto.
- `autosync.js` watches each holder's folder. It drops batches made only of Orca's ignored folders (`.git`, `node_modules`, `dist`, `build`, `.next`, `.cache`, `target`, `.venv`, `__pycache__`) and test output (`test-results`, `playwright-report`, `blob-report`, `coverage`), at any depth. After 300 ms of quiet it runs `spotlight sync --repo <root> --detach --auto` (`--auto`: an automatic sync, see Env). The filter is `watch-filter.js`.
- Env: the settings dialog's env is the repo's default; a pick in the popup or on a task lane's env pill is stored for the task and survives the turn-off (see Env per task). The effective env is the pick stored for the holder's task, else the setting; when it differs from what runs, the server restarts on the next `on` or sync (the reap spawns one, only for Spotlight's own server). When that restart fails, a toast says so, the popup says which env didn't start and marks the one still running, and neither the reap nor an automatic sync (auto-sync, `on`, the reap's own) tries that env again until the settings are saved after the failure, so a server that ignores Ctrl-C isn't sent another one after every save; a lockfile install such a sync restarts for meanwhile runs the env that runs now. Reiniciar, a picked env, a light, Forzar sync and a hand-typed `spotlight sync` always do: each is a new ask, and toasts how it went. A repo waiting in `needs-variant` applies a changed env when its variant is picked.
- Turn-off (`toggle` off, Apagar, Apagar igual) never destroys an untracked root file in the way of a path it writes (the original commit's files, or those of the root's uncommitted changes saved at turn-on), gitignored files included. It looks on disk, without walking ignored folders like node_modules: a file at that path, a file where the path needs a folder, a folder where it needs a file, or, on a case-insensitive disk, a name that differs only in case. Before the reset it commits them, through a temp index, to `refs/herdr-spotlight/rescued/<time>-<sha>`, a ref on no branch that stays after the turn-off. After the restore it writes back on top, unstaged, each one whose exact path is a file of the original commit, so the file keeps its content and reads as an edit of the original. The others are saved and announced but not written back: where the root's own saved changes bring a version of that path (theirs wins), a file/folder conflict, or a case-only name. A toast names the files and the ref, with `git show <ref>:<archivo>` for the ones not written back. A turn-off that fails after saving them names the ref in its error and leaves `refs/herdr-spotlight/rescued-pending`; the next turn-off adds those files to its own save, writes them back and announces them. A fresh activation (not a takeover) drops a pending ref left behind; its ref under `rescued/` stays. A nested git repo in the way (inside a folder there, the folder itself, or above the path) refuses the turn-off with `untracked-collision` before anything is written, since the save could only hold it as a gitlink, and the popup then offers Apagar igual, which discards it, saves the rest and names it in a toast. On a diverged root the `root-diverged` refusal names it too. A submodule of the original commit doesn't refuse: the reset leaves it as it was. Orca has no such guard: its turn-off overwrites them.
- The server popup (`server-view.js`, model `server-view-model.js`) runs the CLI for every control. Proyectar igual runs `light --task <k> --force`, which works inline, through `sh -c 'nohup "$0" "$@" … &'`, so exec's 30 s limit can't cut a lighting short. The argv go in as positional args.

## A busy port before the server starts

Beyond Orca, which neither checks nor frees the port: before typing the server line, Spotlight looks for a process already listening on the port the server will take, and starts nothing while one outside the server terminal's process tree holds it (D23, D24).

- The expected port is the repo's `port` setting when set. Otherwise it comes from `package.json`: the script the command runs, followed through `pnpm|npm|yarn|bun run <s>`, `pnpm|yarn <s>`, `npm-run-all`/`run-p`/`run-s` (globs like `dev:*` included) and `concurrently` (quoted commands and `npm:<s>`), up to three scripts deep. The first `-p N`, `--port N` or `--port=N` on a `next`, `vite`, `astro`, `nuxt`, `remix`, `react-router`, `webpack-dev-server` or `serve` line wins, else a `PORT=N` on it. `pnpm dev` → `npm-run-all --parallel dev:next dev:convex` → `next dev -p 3008` gives 3008. With no port found there is no check. `server-plan.js` `expectedPort` holds the rule.
- The check: `lsof -nP -iTCP:<port> -sTCP:LISTEN -F pcn`, then the listener's pids against the tree under the server terminal's own process (`pgrep -P`), as the ports of a running server are read. A listener in that tree is Spotlight's own server, so a restart goes ahead. A listener outside it refuses the start:
  - `lastError {code: "port-busy", port, pid, command, cwd, message}`, the message reading "El puerto 3008 lo tiene next-server (v16.0.1) (pid 4242, en /Users/…/speaking-english)." The command comes from `ps -o command=`, cut to 120 characters, and the folder from `lsof -a -p <pid> -d cwd`.
  - A toast with that message whose action opens the server popup, once per holder; a line in the server log; nothing typed. `spotlight on` prints the message under the repo's line and doesn't wait for a port that won't open, and `spotlight restart` and `spotlight env` exit 1 with it.
  - A sync doesn't clear the error, and neither does the same workspace lit again: a refused `spotlight restart` over a server that kept listening keeps its `port-busy`. A start that goes through clears it, and so do a takeover whose server needs no start and a plan with no command once no server of Spotlight's may still run there; a start that fails replaces it with its own `server-start-failed` (see "A root error and a server error").
- The popup shows "Liberar puerto y arrancar" on `port-busy` only. It runs `spotlight restart --repo <root> --free-port`: SIGTERM to the process the error names and to its descendants, up to 5 s for them to go, SIGKILL to the ones left, then a normal start. A note records it ("Puerto 3008 liberado: …").
  - It stops that process only while it still holds that port. If another one took it since, that one is shown and nothing is stopped.
  - It never signals pid 1, nor a process whose tree holds the CLI itself or the server terminal's shell.
- That click is the only path that ever stops a process Spotlight didn't start. Agents get the message; `--free-port` is left out of `spotlight --help` and of the skill.
- The pieces are `ports.js` (`portListeners`, `foreignListener`, `stopProcessTree`) and `cli-work.mjs` (`ensureServer`).

## A server that dies at start

Orca leaves such a server "stopped" with nothing said; here it is an error.

- When the server state is `starting` and the terminal's shell is back at its prompt with no port, the server died at start. The reap and `spotlight on` decide it under the repo lock (a busy lock leaves it for the next reap, so a restart in flight is never taken for a death).
- `server-log.js` reads the log after the last `── Spotlight: … · started: … ──` marker, ANSI stripped:
  - `EADDRINUSE`, "address already in use" or Vite's "Port N is already in use" → `port-busy` (the shape above), naming the process that still listens there, or "El puerto 3008 estaba ocupado al arrancar el server." when none does.
  - A server that found its port taken and moved to another didn't die of it: Next's "Port 3000 is in use, trying 3001 instead." (Next 16: "… is in use by process 4242, using available port 3001 instead.") and Vite's "Port 5173 is in use, trying another one..." are warnings, never `port-busy`. The error line after them decides, an `EADDRINUSE` on the next port included.
  - Anything else → `lastError {code: "server-exited", message: "El server se cayó al arrancar: <first error line>"}` (npm's `> ` echo lines skipped, the last line when no line looks like an error, cut at 160 characters).
- One toast per error, opening the server popup; the popup's first buttons read Ver log (the server terminal) and Reintentar (`restart`); the server badge is red with the message as tooltip. `spotlight on` stops waiting and prints the line.
- A change into `listening` or a start that goes through clears it, and so do a takeover whose server needs no start and a plan with no command once no server of Spotlight's may still run there; a sync or the same workspace lit again keeps it, and a start that fails replaces it with its own `server-start-failed`.

## A server that ends by hand

The server runs in the root's "Spotlight" tab (see "Where the server shows"), so it can end by hand while Spotlight stays on (D34). Orca asks before its tab closes ("Turn Off Spotlight & Close"); here there is no confirm, only a toast after.

- When the reap or `spotlight on` sees a lit repo's server that was `listening` read as one of these, it toasts once:
  - `gone`: its terminal ended (the tab or its space closed, or `exit` typed there). "Cerraste la terminal del server de <repo>: Spotlight sigue prendido."
  - `stopped`: its shell is back at the prompt (a Ctrl-C typed in the tab, or the server crashed). "El server de <repo> se detuvo: Spotlight sigue prendido."
- The toast's click opens the server popup. Reiniciar makes the tab again (or types the line again at the prompt) and Apagar turns the root off, as always. On `gone` the popup has no Ver server (nor Ver log): there is no terminal left to show.
- It is decided under the repo's lock (`cli-work.mjs` `settleServerEnd`, the dead start's pattern): the record and the terminal are read again there, and only while the record still says `listening`, on the same start, are the new state, no ports and the note written, in one write. Every restart (a light, a sync's installs, Reiniciar, an env or a variant) holds that lock and leaves the prompt free between its Ctrl-C and the line it types: a reap or `on` that sees that prompt gives up on the lock after 300 ms and leaves the record `listening`, and once the restart lets go the record says `starting`. So a restart is never taken for a stop.
- After the toast the record reads `gone` or `stopped`, so the next looks add none. The server listening again (Reiniciar) makes the next end toast again.
- `starting` → `stopped` is a dead start (see "A server that dies at start"), which toasts its own error and not this.
- The record keeps the server's remembered processes (`serverProcs`), so Apagar still kills a child that escaped holding a port.
- `on` settles it through `recordServers`, which merges nothing for that repo; whichever of the two sees it first toasts, once.
- The pieces are `cli-work.mjs` (`settleServerEnd`, called from `reap` and `recordServers`) and `server-view-model.js` (no Ver server on `gone`).

## Turning the server off

Turn-off (`toggle` off, Apagar, Apagar igual) always leaves the server dead (D26). Orca stops at the Ctrl-C (`spotlight-server-turn-off.ts:48-65`). Here the Ctrl-C comes first too, and is usually all it takes: live on 2026-11-08, a Next server (script → sh pnpm → pnpm → next → next-server) died whole on it. The rest is a safety net for a child that ignores SIGINT, or one that leaves the tree when the Ctrl-C takes its parent.

- Who a listener is. While the server runs, every read of its state (`server.js` `readServerState`: the reap, `spotlight on`, `status`) also names each process that listens under Spotlight's own `script`: `procs: [{pid, start, port}]`, the start time as `ps -o lstart=` prints it with its runs of spaces folded (`text.js` `oneLine`). The CLI keeps these identities on the repo's record and gives them back to the turn-off. A pid is the same process only while its start time is: compared as `ps` prints it, never parsed. The shell's own helpers and a job put in the background there get no identity, and neither does a process `ps` can't place under the `script`.
- One process records an identity (the reap, `spotlight on`) and another checks it (the detached turn-off), and `lstart` prints in the caller's time zone with words of its locale ("Mon Nov 9 01:58:50 2026" against "lun 9 nov 15:58:50 2026" for the same process). So every `ps` read that records or checks an identity runs as `/usr/bin/env LC_ALL=C TZ=UTC ps …` (`ports.js` `PS_ENV` and `psStatesArgv`). The env rides in the argv, not in an exec option: Herdr's `exec` takes none (`cwd`, `on`, `timeout`), so any exec that runs it reads C and UTC. `locks.js` pins `LC_ALL=C` for its own lstart through Node's `execFile`. Identities recorded before this carry the old locale's and time zone's words: they match nothing, which is the same as a record with no identities, and the next reap or `on` drops them as gone.
- Before the Ctrl-C, `server.js` `stopServer` reads the server:
  - Every process under the server's own process (the `script` Spotlight typed, which leads the terminal), each with its start time and command (`ps -o pid=,ppid=,stat=,lstart=`, `ps -o pid=,command=`). The `script` must be the shell's child and every process below it its parent's child, as `ps` reads them; a pid that changed hands between the reads is left out.
  - The ports those processes listen on, plus the ports recorded for the server and those of its identities.
  - Who else listens on those ports from outside the terminal, but only a process whose pid and start time match one of the recorded identities: a server child that left the tree earlier.
- A server started by hand on one of those ports, in the root or not, is never touched: it has no identity. The same goes for a process that got a recorded pid later (another start time). This holds on every path: with the server running, at a free prompt and with the terminal gone. Only "Liberar puerto y arrancar" (a click, D24) ever stops a process Spotlight didn't start. A record from before identities existed carries none, so its turn-off kills no listener outside the tree; the server's own tree, read from its pid at the turn-off, is killed as always.
- The terminal's shell is no part of the server, and neither are its own helpers (powerlevel10k's gitstatusd, a zsh-async worker, a job put in the background): they are never waited on and never signalled.
- After the Ctrl-C, the stop waits up to 8 s for the prompt to come back and these leftovers to be gone:
  - A process of the server that still runs as the same process (same pid, same start time, not a zombie), wherever it went. One the Ctrl-C reparented to launchd counts, even if it listens on nothing: spotlight-lab's `rama-terca` runs `(trap '' INT TERM HUP; exec sleep 900) &` next to `next dev`, and that `sleep` is killed. A pid another process took since (another start time) is never a leftover.
  - A recorded listener read before the Ctrl-C, outside the terminal, still on one of those ports and running inside the root (`lsof -a -p <pid> -d cwd`). One running outside the root is never a leftover, and neither is one in a folder that only shares the root's name as a prefix.
- When hc can't send the Ctrl-C, the stop doesn't give up and doesn't wait: what it read before is killed at once. The result carries `interruptError`.
- Leftovers still there after the 8 s are killed together with whatever runs under them now: SIGTERM, up to 3 s, then SIGKILL. A zombie counts as gone. Each process's children are read once (`pgrep -P`), however the leftovers' trees overlap.
- The server log says which: "Spotlight off — server stopped (interrupt sent)" or "Spotlight off — server stopped (forced: 2 processes)". A Ctrl-C hc couldn't send goes in the same parentheses: "(forced: 3 processes; the Ctrl-C could not be sent: herdr-core unreachable)", or "(nothing left to kill; the Ctrl-C could not be sent: …)" when the server was gone without it. hc's words go on one line; with none, just "the Ctrl-C could not be sent".
- A failed stop (`ok: false`) always means the server may still be up:
  - `survived`: a process still alive after the SIGKILL (not ours to signal, or stuck in the kernel), or a leftover never signalled because its tree holds the CLI itself or the terminal's shell (`refused`, counted among the survivors). The server did not die (S17). The log says "Spotlight off — server NOT stopped: 1 processes survived (pids 4242)", with "; not signalled: 4242" for a refused one and "; the Ctrl-C could not be sent: …" when hc couldn't send it.
  - `unreadable`: hc can't read the terminal, so there is no server pid to read and nothing is signalled.
  - `interrupt-failed`: the Ctrl-C couldn't be sent, and afterwards neither hc nor `ps` showed anything to kill or showed the server gone.
  - `still-running`: its processes were killed, but hc still shows Spotlight's old `script` (its `pid`) in front.
- Any `ok: false` fails the turn-off. The root is restored all the same, the CLI exits 1, and an error toast replaces "Spotlight off — root restaurado". `survived` gives `server-survived`, naming who lived through SIGKILL and who couldn't be signalled. Every other reason gives `server-not-stopped`: "El server no paró al apagar Spotlight: <detalle> (el root sí se restauró)." The detail is Spanish only, one per reason, never `stopServer`'s English message (which says again that the server may still be running): "hc no pudo mandarle Ctrl-C ni leer su terminal", "el proceso 4242 siguió corriendo en su terminal", "hc no pudo leer su terminal", and for a reason the CLI doesn't know yet "Spotlight no pudo confirmar que paró (<reason>)". These two codes are `TURN_OFF_ERRORS` (`server-errors.js`, which defines them for `cli-work.mjs`): never stored on a record, only toasted and printed.
- What `stopServer` says in its own words (hc's or `ps`'s cause, and a Ctrl-C hc couldn't send) goes into the server log instead, so `spotlight logs` shows it after the record is gone. `stopServer` writes it itself, in its one note, at every return that didn't stop the server: "Spotlight off — server NOT stopped (unreadable): the Spotlight terminal could not be read (hc: no route to core): the server may still be running", likewise for `interrupt-failed` and `still-running` (the latter with "; the Ctrl-C could not be sent: …" when hc couldn't send it), and the `survived` line above. Those four reasons are `server.js` `NOTED_STOP_FAILURES`. The turn-off adds a stop line of its own only for an answer `stopServer` wrote none for (no answer at all, or a reason outside those four): "Spotlight off — server NOT stopped (no answer)", or "(<reason>)" with the answer's own words after it when it has some. So each stop leaves one line. It is written before the restore, so a restore that refuses next keeps it too.
- When the stop fails and the restore then refuses too (the root changed during the stop, say), the turn-off reports both in one toast and one line, with the git error's code and exit 1: "<git error>. Además, el server no paró: <detalle>." The record keeps only the git error, the root error the popup acts on.
- The identities live on the record as `serverProcs`: every `procs` the reap and `spotlight on` saw while the repo was lit, across restarts, one per pid and start time, the newest 32 (`cli-work.mjs` `rememberProcs`). A restart keeps them: an old child that escaped holding 3000 while the restarted server moved to 3001 still dies at the turn-off. Before each look merges what it saw, the identities that no longer run as that process (the pid gone, a zombie, or another start time) are dropped, read with one `ps` before the state write (`ports.js` `goneIdentities`; when `ps` can't say, none is dropped). That `ps` asks only for the records the look then writes: a repo waiting for a variant, or a dead start left `starting` because its lock was busy, gets none. The write merges only the repos that read picked, judged again on the record as written: one that turned mergeable in between (a variant picked, a dead start settled) has no `ps` behind it and waits for the next look. Neither `on` nor the reap merges a look into a record restarted since (Reiniciar, a lockfile, an env: `starting` again with a new `serverStartedAt`): the old server's `listening`, ports and processes would hide the new one's death at start. Nor into one that turned to wait for a variant since the look: both writes judge by the same rule (`cli-work.mjs` `mergesInto`). So a watch-mode server that respawns its listener on every save never pushes a live escaped listener out of the 32. `ports` stays what listens now. The turn-off passes `procs: serverProcs` and the live `ports`; `serverSnapshot` adds the ports of the identities itself.
- An identity is a valid pid and a start that is a non-empty string (`ports.js` `isIdentity`), the same rule for what the record keeps and what the turn-off reads.
- With the prompt already free (the server had stopped on its own), or no server terminal at all, nothing is interrupted, but a recorded listener on a recorded port running inside the root is still killed, at once. The result lists it under `escaped` and the log says "(forced: 1 processes)".
- Never killed:
  - The terminal, its shell and the shell's helpers. The terminal stays for the next start, as in Orca.
  - The CLI itself: a leftover whose tree holds it is left alone, and the stop says the server was NOT stopped.
  - Anything that started after the Ctrl-C, such as a restart typed into the terminal during the wait, and any listener Spotlight never recorded, such as a server started by hand in the root. Spotlight's own starts and restarts can't land in the wait anyway: the stop runs under the repo's lock, which every start takes.
- A process Spotlight didn't start in front of the terminal: nothing is sent or killed.
- Every signal goes through the injected `kill` (`deps.kill`, process.kill's shape). `stopServer`, `stopLeftovers` and `stopProcessTree` throw without one; nothing falls back to the real `process.kill`.
- The pieces are `ports.js` (`treeListening`, `serverSnapshot`, `serverLeftovers`, `stopLeftovers`, which share T13's TERM-then-KILL with `stopProcessTree`; `PS_ENV`, `psStatesArgv`, `isIdentity`, `goneIdentities`), `server.js` (`readServerState`, `stopServer`) and `cli-work.mjs` (`rememberProcs`, `recordServers`, `deactivateRepo`, `turnOffError`).

## A root error and a server error

`lastError` holds one root error (any code but the server errors) and one server error (`SERVER_ERRORS`, `server-errors.js`: `port-busy`, `server-exited`, `server-start-failed`, exported as `PORT_BUSY`, `SERVER_EXITED`, `SERVER_START_FAILED`). The root error is on top, with the server error under it as `lastError.serverError`. A turn-off's `server-survived` and `server-not-stopped` are another set, `TURN_OFF_ERRORS`, whose codes `cli-work.mjs` takes from `server-errors.js`: the record is gone with the turn-off, so they are never on it, and nothing that reads a record (the badges, the popup, `serverDown`, the error stack) ever sees them.

- Writing a root error keeps the server error underneath. Clearing it (a sync, Forzar sync that goes through, or Orca letting go) gives the server error back.
- A lighting that goes through clears the root error. The server error is decided by the server's start (`cli-work.mjs` `ensureServer`, never the lighting itself), and by who lights:
  - A start that goes through clears it. A port still taken writes `port-busy` again (one toast per new error: the same process on the same port doesn't toast again).
  - A start that fails writes its own, `server-start-failed`, over whatever server error was there, so the record never blames another start's pid or port: "El server no arrancó: <motivo>", the motive in Spanish only, one per reason (hc couldn't read, make or type into the server terminal, its terminal runs another program: "su terminal corre otro programa (no se tocó)", it closed): "El server no arrancó: hc no pudo leer su terminal". hc's own words go to the server log, in the start's own line, never into the error or its toast: "Server not started — the Spotlight terminal's state could not be read (hc: no route to core)" (`server.js` `startServer`, `restartServer`; an invalid command touched no terminal and leaves none). No new server runs and the record says why, whoever lights. It toasts, opening the popup, which offers Ver log (none when its terminal closed: the record reads `gone`) and Reintentar, and the server badge is red, as with `server-exited`. Whoever asked for that start hears how it went every time, the same failure too: a light, Reiniciar, Reintentar, Liberar puerto, a picked env or variant. An automatic sync's server work (auto-sync, `spotlight on`, the reap's sync for a changed env) toasts it once per new error; Forzar sync and a hand-typed `spotlight sync` toast it every time. When Spotlight's old server may still lead its terminal (it was in front, or hc couldn't read the terminal, and the start never typed its line), the record keeps the state it had and the cause of a stuck restart.
  - An old server that never let go of the prompt and still runs is no failed start: it ignored the Ctrl-C, or hc couldn't send it (`restartServer`'s `oldServerRuns`). When hc couldn't send it, the terminal is looked at again first, as the turn-off does: only Spotlight's server still in front, or a terminal hc can't read, still runs; one that closed meanwhile is a failed start ("su terminal se cerró"), and one back at its prompt gets the line typed. The record keeps the state it had and gets no server error of its own; `ensureServer` answers `still-running`, its own state: the light's toast reads "Spotlight on · <repo> ← <workspace> · server sin reiniciar", and `spotlight restart` and `spotlight env` say "the server did not restart: the old one still runs (<reason>)" and exit 1. Its toast says so every time someone asked for that restart (a light, Reiniciar, Reintentar, a picked env or variant): "el server sigue corriendo: no paró con Ctrl-C y no se reinició", or "…: hc no pudo mandarle Ctrl-C y no se reinició". An automatic sync repeating the same cause doesn't toast again (the record's `restartStuck`: the reason, env and planned command; another env, or a settings save that changes the command, is a new ask and toasts. A start drops it, and so does a start that fails unless the old server may still lead its terminal), and an automatic sync doesn't try that env again until settings are saved (above). The log has the start's own line ("Server not restarted — …", with hc's words, else its error's kind). That server is still up, and a server error would hold back the reap's retry of a changed env (J-011).
  - A plan with no command clears it once no server of Spotlight's may still run there: no server terminal, by the record's address or by its name (`sl-<slug>`, as every start looks for it), or one that shows something other than Spotlight's own server in front. Spotlight's server in front, or a terminal hc can't read, keeps it. With none, there is no server to be wrong about; one of before still running (an env with no command, a variant that can't be filled) keeps its `port-busy` and "Liberar puerto y arrancar".
  - A takeover whose server starts nothing new and records nothing new (a variant to pick, no command, the same command already running, an old server that never let go of the prompt) clears it: the server error a last holder left (its dead start, its busy port) says nothing of the new one. A takeover is any fresh activation: another workspace, Proyectar igual, or the workspace the record already names when its refs were gone. A fresh activation is a holder switch all through the light: the log's holder header, the "Spotlight on · … ←" toast, and the lockfiles compared from what the refs it found say the root had: the snapshot they projected when they were active (also with no record, or one whose `lastSnapshotSha` is stale), or the root's own HEAD when it had moved off that snapshot (a diverged root under Proyectar igual), else the root's own HEAD.
  - The workspace that already holds the root lit again on its own refs (a relight of its turn, which only syncs it) keeps it in those cases, as a sync does: a `port-busy` a refused `spotlight restart` left over a server that kept listening stays (D24).
- A dead start, a busy port or a failed start under a root error goes underneath and toasts as it would on top. The toast says the root comes first: "<server error> Antes resuelve el root: <root error>", the root error on one line, since the popup shows the root error and can't act on the server's until it is resolved. It opens the popup only when the popup can act on that root error (Forzar sync, Apagar igual); under `orca-holds` it opens nothing.
- A listen, or a start that goes through, clears the server error wherever it is.
- `status --json`, the badges, the popup and the hook show the top error; `spotlight on` reports the server error in force.
- Every writer goes through `setRootError`, `setServerError`, `clearRootError` and `clearServerError`. `store.js` `reconcileRepo` writes `lastError` itself, so `cli-work.mjs` wraps it (`underRootError`).

## A root Orca's Spotlight holds

While both apps run, Orca Pro Max's Spotlight can take a root this plugin holds (seen on 2026-11-08: Orca reset the root under Herdr's holder). The two must never fight over it.

- The sign: the root's HEAD is detached on a commit authored exactly "Orca Spotlight" (`git cat-file commit HEAD`). An attached HEAD never counts.
- Turning on, syncing and turning off refuse with `lastError {code: "orca-holds", message: "Este root lo tiene el Spotlight de Orca: apágalo allá primero."}` and leave the root as Orca left it. No `--force` gets past it; the popup shows the message and no Forzar sync, Proyectar igual or Apagar igual.
- The reap's reconcile keeps `orca-holds` instead of flipping it to `root-diverged`, and drops it once Orca lets go (back on our snapshot: cleared; anywhere else: the usual `root-diverged`).
- Not caught: when Orca lit a clean workspace its snapshot is the user's own commit, so the root reads `root-diverged`. Orca's `refs/orca/spotlight/*` would tell, but stale ones stay behind for weeks and would block legitimate turn-offs.
- The pieces are `sync.js` (`orcaHoldsRoot`, checked before every git step of on, sync and off) and `cli-work.mjs` (`reconcileWithOrca`).

## Continuar and auto-resume

When an agent's turn ends in an error, a sign-in prompt or a usage limit, its request is paused in place (D13). Continuar picks it up again, like Orca. The rules are `resume.js` (pure, shared by the board and the CLI); the CLI side is `cli-resume.mjs`.

- `spotlight continue --terminal <t> [--account <id>]` opens the resume window (3 min) under the state lock, starts a detached `continue --inline` and returns at once. A second Continuar while the window is open, or while the plugin's job runs, reuses it.
  - A paused agent, with the claude-accounts plugin: a fresh `claude-accounts usage --refresh`, then the account with the lowest peak under 100% over session, weekly, fable and monthly (the active one wins a tie; accounts that need a sign-in, carry an error or have no known usage never win), then `claude-accounts resume --terminal <t> --account <id> --message "Continue where you left off." --json`. Every account full: "Vuelve a las <hora>", the earliest of each account's latest full-window reset.
  - A paused agent without the plugin: the message is typed into the same agent (`hc send`).
  - An idle holder (the board's flagged testing row): Esc, then the message, in the same account. It keeps its turn; the Esc's turn end is spent.
  - A `signin` pause is never switched to another account: the board offers Inicia sesión, which runs `claude-accounts.open-accounts`.
- The reap (and `on`, `off`) polls `claude-accounts resume --status <job>` while the job lives, which keeps the window open. Its final state is cached on the request the first time it is seen, so a job the plugin forgets after 24 h (exit 7) changes nothing.
  - `done`: the pause ends, and the request asks for its place back at the front of the line, granted when its repos are free. The turn count is re-baselined, so the resumed session's first turn end is decided like any other.
  - `timeout`, `landedElsewhere`, `failed` (its `detail` carries the manual `claude --resume <sid>`) and `cancelled`: the agent stays paused with that text on its board row, and the window closes.
  - A terminal that left inside the window is released when the job settles, if the job failed or the terminal is still gone.
- Auto-resume (settings, off by default): the reap starts `continue --auto` for `limit` pauses only, at most 3 delivered in a row. With no account left it tries again 60 s after the first reset. Each delivered one leaves a toast, "Reanudado con <cuenta>: <tarea>".
- `spotlight classify --terminal <t>` is spawned by the reap when a turn end needs the account's usage and the usage in `accounts.v1.json` is over 2 min old. It refreshes the usage, then releases the turn or pauses it (`limit`, `signin`, `error`). A classify that died, failed to spawn or got stuck (no answer in 90 s) is spawned again, up to 3 times per turn; after that the reap decides with the last usage it read.
- An `accounts.v1.json` whose `version` isn't 1 is refused: Continuar says so, and turn ends are decided as without the plugin.
- Spotlight never runs `claude-accounts use`, since that changes the global active account.

## Terminals with no task

A Herdr terminal on a main checkout or a non-git folder (or a worktree whose branch and folder can't name a task) still gets a test turn: `spotlight on` takes a slot-only turn keyed `cwd:<realpath>`, so two terminals in one folder share it, in the group holding its repo, else `spaceless`. It lights nothing. `on` with no `--terminal` and no `$HC_TERMINAL_ID` exits 2.

A `spotlight on` typed in a plain shell records the shell's pid as the agent, so the prompt coming back doesn't release the turn. A wrapper (`sh -c 'spotlight on; …'`, `make`) records the wrapper's pid and still releases when it ends.

## Settings

The settings dialog (the board's gear; `settings-view.js`, model `settings-form.js`) edits `settings.json`, which only the mod writes. From Orca's repository settings (D37):

- Each command field (Local, Dev, Prod) has a "▾" beside it listing the repo's package.json scripts whose names start with dev, local, prod or start, as commands for its package manager (`pnpm dev`, `npm run start --`): `server-plan.js` `detectServerScripts`' `scriptCommands`, read in the root as the server popup reads it. A pick fills the field; the save still checks it. A repo with nothing to suggest has no "▾".
- A field's placeholder is the command that runs while the field is empty: the other envs' saved commands, then the detected scripts; Local falls back to Dev; `{variant}` stays unfilled and no `--port` is added (the port has its own field). "No arranca" when nothing would run. Herdr's InputState has no placeholder setter, so the inputs are made once detection is in, and the placeholders are those of the settings as the dialog opened.
- Apagado on a lit repo turns it off first, as Orca does. Guardar writes every other field with that repo's `enabled` unchanged, keeps the dialog open with "Apagando Spotlight en <repo>…", reads `state.json` again and, while the repo still has a record there, runs `spotlight toggle --workspace <root> --inline` (up to 120 s). Named by its root, the repo only ever turns off, whoever holds it now. When it went off, or the CLI answers `root-is-holder` (nothing was lit any more), `enabled: false` is written (compare-and-swap, read again if settings.json changed meanwhile) and the dialog closes. A turn-off that fails leaves the switch on, as saved, and the dialog shows the CLI's first line; the turn-off's own error toast still comes from the footer. A repo that isn't lit, or one already Apagado, just saves. When `state.json` can't be read, the dialog can't tell whether the repo is lit, so it asks the CLI anyway.
- The save runs in a task no view owns: Herdr's Esc may close even a modal dialog, and a closed dialog's own tasks die after 250 ms, which could leave the repo off with the switch still on. Esc and Cancelar do nothing while it runs. If the dialog closed anyway, a failure comes as a toast ("Spotlight sigue encendido en <repo>").
- With a queue value changed too, `spotlight reap` runs once at the end, after the turn-offs.

## Busy

While Spotlight works on a repo, its flashlight is a spinning ring, as Orca's "syncing" state (D33).

- What marks a repo busy: every light (a flashlight click, an agent's turn, Proyectar igual), every turn-off (Apagar, Apagar igual, Apagado in settings), a Forzar sync (`sync --force`), and a server restart (`spotlight restart`, Liberar puerto y arrancar, `spotlight env --env` or `--variant`). Auto-sync and the sync `spotlight on` runs never do: they run on every save, and the ring would flash.
- The mark is the repo record's `busy: {op, since, pid, workspace}` in `state.json`. `op` is `light`, `off`, `sync`, `restart`, `env` or `variant`. `workspace` is the target: the workspace being lit, or the holder being turned off or synced (null for refs nobody holds).
- It is set under the repo's lock and cleared in `finally`, whether the work went through, was refused or threw. Work inside a mark, such as a light's server start, adds no mark of its own.
- A fresh light (no holder yet) makes the repo's record for the mark, so the target's row spins before it holds, like Orca's optimistic holder. A light that ends having written nothing drops that record again.
- On the rows, the holder's and the root's flashlight, and the target workspace's, become the ring (`icons/spinner.svg`, `spin: true`), with the tooltip "Sincronizando…" and no action. The server badge, the queue badge and the other workspaces' flashlights stay.
- A process that dies before its `finally` leaves its mark behind. The reap (the footer's, every 30 s and on terminal changes) clears a mark whose pid is dead, or alive but started after the mark (pid reuse: `ps -o lstart=`, `locks.js` `isStale`). It reads that before taking the state lock, and clears the mark only if it is still the same `(pid, since)`, so a mark a new light set in between stays. `spotlight on` and `off` don't clean marks.
- For the whole-task toggle (D31):
  - `queue.taskBatch[<groupId>/<KEY>] = {op, since, pid}` while a batch runs (`cli-work.mjs` `withTaskBatch`), cleared the same two ways.
  - `lightTask(cx, key, { quiet: true })` and `deactivateRepo(cx, root, { quiet: true })` leave out the per-repo "Spotlight on · …" and "Spotlight off — root restaurado" notes. Errors, warnings and rescued files still toast.
  - `quiet` is a call option, never stored on the lighting marker, so a later Proyectar igual of that marker toasts as usual.
- The pieces are `store.js` (`markBusy`, `clearBusy`, `setTaskBatch`, `clearTaskBatch`; a malformed mark or batch is dropped on read), `cli-work.mjs` (`withBusy`, `withTaskBatch`, `staleMarks`) and `badges-model.js` (the ring).

## The task button

In a group organized by Task, each task lane's header carries Spotlight's flashlight, Orca's "Spotlight this task" (D31, D29): one click lights the whole task, or turns it off, in every project of the group.

- Who takes part: each project of the group with a workspace of the task (a main checkout never is one) whose Spotlight is on (its setting, else the default: a repo with a server command). With several workspaces there, the one holding the root, else the one whose agent changed status last, else the newest commit, as `spotlight on` picks. Projects with Spotlight off are skipped and named in the tooltip ("Saltado, Spotlight apagado en: admin-action"). Orca spans every worktree; here only the group's projects count (D12). With nobody left, the lane has no flashlight.
- Amber (working) when every project's root is held by one of the task's workspaces there, dim otherwise. The tooltip says what a click does: "Spotlight de esta tarea: proyecta sus workspaces en el root de cada proyecto." or "Spotlight prendido para esta tarea. Clic para apagarlo en todos los proyectos."
- A click runs `spotlight toggle --task <KEY> --group <id>`, which hands the work to a detached `--inline` copy and answers at once (D18):
  - Lit: each project is turned off in turn: the root restored, its server stopped.
  - Not lit: first every project of the group lit by no workspace of the task is turned off, then each project the task doesn't hold yet is lit, taking it over from whoever holds it. The ones already held stay as they are.
  - One project failing never stops the rest, and each failure toasts itself as a workspace's would (its popup action included). The projects say nothing else: one toast sums the batch up, "Spotlight on · AX-3653" / "Spotlight off · AX-3653" when every project went through, "Spotlight on en 1 de 2 proyectos" / "Spotlight off en 1 de 2 proyectos" when some did, none when none did.
  - Each project is lit through its `direct/<root>` marker, as the workspace flashlight lights it, so Proyectar igual on a refused one works and toasts as usual.
- While the batch runs (`queue.taskBatch[<groupId>/<KEY>]`) or one of its projects is busy (see Busy), the flashlight is the ring: spinning, "Sincronizando…", no click. Orca's button also spins while it works ("Updating Spotlight…").
- After it, the task's env pill (see Env per task), then the task's queue badge (testing, #N in line, paused), the one its workspace rows show, so a folded lane still says it. With the queue off, none.
- `<KEY>` is the lane as projects-sidebar keys it: a ticket ("AX-3653") or the name lowercased; the CLI also takes a ticket in any spelling (`ax_3653`). `--group` is the projects.v1 group id. A missing `--group`, an unknown group or a key that can't name a task exits 2; `--inline` exits 1 when no project can take part or none went through.
- Spotlight publishes the lanes of every Task-mode group under `badges.spotlight`, keyed `<groupId>/task:<KEY>` (projects-sidebar's "Badges from other plugins"), whichever group is shown: a lane name can repeat across groups. A group organized by Project gets none.
- The pieces are `task.js` (`resolveGroupTask`, `taskLit`, `taskKeyFrom`), `cli-task.mjs` (`toggleTask`, `summaryOf`), `badges-model.js` (`taskModeGroups`, the lane badges) and `cli.mjs` (the verb).

## Env per task

Every env pick is stored in `state.json`'s `envs`, keyed by task, and survives the turn-off (D32, Orca's TaskSpotlightEnvPill). One pick sets the env of the whole task in that space.

- The key: `<groupId>/<KEY>` for a workspace of a task (its lane, as `state.variants` keys it: the projects.v1 group, else `spaceless`), `ws:<path>` for a workspace with no task (a branch and folder that name none). Another workspace of that repo doesn't inherit a `ws:` pick, and the same task in another space is another key. `envs` keeps the newest 500 picks: a new one drops the oldest.
- A light writes its holder's key on the repo's record (`envKey`: the turn's or the batch's task, else the workspace's), so the env in force needs no git: `envs[envKey]`, else the repo's settings env. A record lit before T22 has no `envKey`: it reads its old `envOverride` while the same workspace holds it, so installing T22 restarts nothing; any other light keys it. `envOverride` is never written again.
- `spotlight env --task <KEY> --group <id> --env local|dev|prod` (the pill's popup) stores the pick before it answers, then a detached `--inline` copy (D18) runs it on every lit repo whose holder has that key, one after another, each busy while it works (op `env`). The copy gets no `--env`: it runs what is stored when it gets there, so two picks in a row end in the last one. A missing `--group`, an unknown group, a key that can't name a task, a missing or unknown `--env`, or a `--workspace` or `--variant` beside `--task` exits 2.
- An explicit pick restarts Spotlight's server only when its command changes (Orca's `restartIfDifferent`): with only a `dev` script, Local runs Dev's command, so switching between them types nothing and the record's `serverEnv` just follows. An env with no command leaves the server as it was. A pick that does restart is an explicit request, as Reiniciar: a failed start or an old server that ignores Ctrl-C toasts every time. A settings change, picked up by `on`, auto-sync or the reap, still restarts on any env change (J-002).
- `spotlight env --workspace <p> --env <e>` (the server popup) stores the pick under that workspace's key: a task workspace writes its task's. It reaches the server only when the repo's holder has that key (the workspace holds the root, or another workspace of its task does); a workspace that doesn't hold the root just stores it ("<repo>: env dev saved."), and its next light runs it.
- Any pick adopts a lit record with no `envKey` whose holder's key it is: in the same write, the record takes the key and drops `envOverride`, so the pick restarts it once and the reap leaves it alone after.
- The pill: on a task lane's header, after the flashlight and before the queue badge, the server icon, dim, and the env's name ("Local", "Dev", "Prod"). With nothing stored, the env the held repos run; when they differ, "Mixto", each repo's env in the tooltip ("Entorno de Spotlight de esta tarea: mixto (back Local · front Dev). Clic para elegir uno."). Shown as Orca shows it: while a member holds its root, or when the stored env isn't Local; with no flashlight, none. Today it draws with the badge contract (an icon and the text); T31 makes it D39's text badge.
- A click on the pill sends `spotlight.env.<id>` (the id: sha1 of `<groupId>/<KEY>`, first 12 hex), which opens the env popup at the pointer (`env-view.js`): Local, Dev and Prod, the pill's value checked (none for Mixto, with each repo's env under). A click on another runs `env --task`; the popup closes when it answers, or shows why it failed.
- The server popup selects the same env: the holder's (its key's stored pick, else the settings env), and on a root nobody holds, the one stored for the workspace it was opened from (its task read from projects-sidebar's lists), which that workspace's light would start.
- The pieces are `task-env.js` (the keys, `recordEnv`, shared by the CLI and the mod), `store.js` (`rememberEnv`, `ENVS_MAX`; a malformed entry or `envKey` is dropped on read), `cli-work.mjs` (`effectiveEnv`, `writeEnv`, `applyEnv`, `lightMember`'s key), `cli.mjs` (the verbs), `badges-model.js` (`laneEnv`, `laneEnvChoices`, the pill), `badges.js` (the command), `env-view.js` (the popup) and `server-view-model.js`.

## The workspace menu

Spotlight adds its items to a workspace's right-click menu in projects-sidebar, after projects-sidebar's own items and a separator, as Orca's worktree menu does (D30; projects-sidebar's "Menu items from other plugins").

- What each row gets:
  - A worktree of a repo with Spotlight on: "Proyectar este workspace" (a takeover when another workspace holds the root), or "Apagar Spotlight" on the holder; then "Entorno de Spotlight ▸" with Local, Dev and Prod.
  - The holder of a root that diverged (`root-diverged`): "Forzar sync" too, between the two, in red (`danger`), Orca's "Force Sync Spotlight (overwrite root changes)"; its tooltip says it overwrites the root's changes. Never for another error.
  - The root's own row while Spotlight is on there, whatever the repo's setting (Orca's turn-off on the main checkout), or while refs nobody holds are left (`orphan-refs`): "Apagar Spotlight" alone. Unlit, the root has no items: the main checkout never holds the root.
  - A repo with Spotlight off: nothing on its worktrees.
- Every item runs the CLI through an exec, as the badges do: the toggle `spotlight toggle --workspace <path>` (the row's flashlight), Forzar sync `spotlight sync --repo <root> --force --detach` (the server popup's), an env `spotlight env --workspace <path> --env <e>`. The menu stays open with the row's "…" while it runs; a non-zero exit toasts stderr's first line (a refused turn-off says `root-diverged: …` and how to force it).
- The env checked is the one the server popup and the task lane's pill show (see Env per task): on the holder, the env its server runs (its record's key, or `envOverride` on a record lit before T22); on any other workspace, the pick stored for its key (its task's `<groupId>/<KEY>`, else `ws:<path>`), else the repo's settings env. A pick stores it for the workspace's task, so it sets the env of the whole task there, and restarts only this repo's holder when it has that key. Unlike the popup, all three envs are listed, as in Orca, even one with no command: picking it stores it and leaves a running server alone.
- While the repo is busy (see Busy), the toggles and Forzar sync are disabled, their hover saying "Sincronizando…"; the env submenu stays, as in Orca.
- The footer copy publishes it under `menus.spotlight` (`badges.js`), from the same readings as the badges, only when the value changes, and clears it with the badges when it closes. The model is `menus-model.js`; its test checks every item with projects-sidebar's own parser.
